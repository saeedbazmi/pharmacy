# init — M1: یک داروخانه سرتاسر

این فایل نقطه‌ی ورود به Milestone است. کامل بخوانش، سپس `plan.md` کنار آن را.

## ترتیب مطالعه

1. `AGENT.md` — بخش ۴ (مدل داده) و ۵ (خط داده).
2. `plans/m1-single-pharmacy-pipeline/plan.md`.
3. `features.md` — بخش «تیم محتوا و داده» برای درک اینکه در M4 چه چیزی روی این خط داده سوار می‌شود.

## Skill فعال

- `backend-dev` برای PH1-009، PH1-010، PH1-012، PH1-013.
- `frontend-dev` برای PH1-011.

## وضعیت موردانتظار ریپو

- [ ] دروازه خروج M0 کامل است.
- [ ] اسکیمای هسته مایگریت شده و `sqlc` کار می‌کند.
- [ ] کلاینت `lib/api` در فرانت آماده است.

## راه‌اندازی

```bash
make up
make migrate
make worker   # اجرای محلی worker برای دیدن نتیجه سینک
```

نمونه‌ی خروجی منبع را پیش از نوشتن Fetcher در `backend/internal/module/ingest/testdata/` ذخیره کن؛ توسعه و تست روی همان فایل انجام می‌شود، نه با کرال زنده.

## ترتیب اجرای پیشنهادی

PH1-009 → PH1-010 → PH1-012 → PH1-013 → PH1-011.

دلیل: تا offer واقعی در دیتابیس نباشد، صفحه کالا چیزی برای نمایش ندارد. فرانت می‌تواند با داده‌ی نمونه‌ی ثابت جلوتر شروع کند، اما پذیرش نهایی روی داده‌ی سینک‌شده انجام می‌شود.

## تصمیم‌های باز

- کدام داروخانه منبع اول است و آیا API دارد یا باید کرال شود؟
- بازه‌ی زمانی سینک (هر چند دقیقه) برای منبع اول چقدر باشد؟
- در نبود کد یکتا (IRC/GTIN) در داده‌ی منبع، آستانه‌ی تطبیق چه باشد؟ (پیشنهاد: در M1 هیچ تطبیق فازی انجام نشود و همه به صف تایید برود.)
