# init — M4: پنل تیم داده

این فایل نقطه‌ی ورود به Milestone است. کامل بخوانش، سپس `plan.md` کنار آن را.

## ترتیب مطالعه

1. `features.md` — بخش «تیم محتوا و داده»؛ این Milestone مستقیماً همان فهرست است.
2. `AGENT.md` — بخش ۴ (مدل داده)، ۵ (تطبیق و آستانه)، ۷ (گروه مسیرها و نقش‌ها).
3. `plans/m4-data-ops-panel/plan.md`.

## Skill فعال

- `backend-dev` برای مسیرهای `/api/v1/ops/...`، نقش‌ها، audit و ترنزکشن تطبیق.
- `frontend-dev` برای صفحات `app/(admin)`.

## وضعیت موردانتظار ریپو

- [ ] دروازه خروج M3 کامل است.
- [ ] `match_candidates` از M1/M2 داده‌ی واقعی `pending` دارد.
- [ ] جست‌وجوی کالا کار می‌کند (برای اتصال دستی در صف تطبیق لازم است).

## راه‌اندازی

```bash
make up
make migrate           # جداول کاربر داخلی، نقش، audit_logs
make create-ops-user   # ساخت اولین کاربر data_ops برای توسعه
```

## ترتیب اجرای پیشنهادی

PH1-026 → PH1-031 → PH1-027 → PH1-028 → PH1-030 → PH1-029 → PH1-032.

دلیل: احراز هویت و audit باید پیش از هر صفحه‌ی تغییردهنده‌ی داده وجود داشته باشند، وگرنه بعداً باید همه‌ی مسیرها بازنویسی شوند. صف تطبیق (PH1-028) سنگین‌ترین آیتم است و ارزش بیشتری از مدیریت دسته‌بندی دارد.

## تصمیم‌های باز

- کاربر داخلی با نام‌کاربری/گذرواژه وارد شود یا OTP پیامکی مثل کاربران عادی؟ (پیشنهاد: گذرواژه + محدودیت نرخ، چون اپراتور روزانه وارد می‌شود.)
- آستانه‌ی امتیاز شباهت که تطبیق را خودکار می‌کند چند باشد؟ پیش از تعیین، توزیع امتیاز داده‌ی واقعی را نگاه کن.
- آیا ویرایش دستی مشخصات کالا باید همه‌ی فیلدها را قفل کند یا فقط فیلد ویرایش‌شده؟ (پیشنهاد: فقط فیلد ویرایش‌شده.)

## هشدار امنیتی

این Milestone اولین جایی است که نوشتن روی داده از بیرون ممکن می‌شود. سه چیز غیرقابل مسامحه است: بررسی نقش در middleware، اعتبارسنجی URL منبع برای SSRF، و ثبت audit برای هر تغییر.
